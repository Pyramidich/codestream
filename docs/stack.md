# Обоснование стека CodeStream backend

> Цель: выбрать технологии для backend пet-проекта CodeStream — онлайн-редактора кода с совместным редактированием в реальном времени.

---

## 1. Web-фреймворк

### Сравнение Fiber, Gin, Echo

| Фреймворк | Плюсы | Минусы | Verdict |
|-----------|-------|--------|---------|
| **Gin** | Самая большая экосистема и комьюнити, много middleware, простой API, стабильный. | Не самый быстрый (но разница несущественна для MVP). | ✅ **Выбран** — стандарт де-факто, лучше для портфолио. |
| **Fiber** | Максимальная производительность (fasthttp), синтаксис похож на Express.js. | Меньше плагинов и примеров, fasthttp может конфликтовать с некоторыми middleware. | Подходит, если критична скорость. |
| **Echo** | Чистый API, хорошая встроенная валидация, стабильный. | Чуть меньше экосистема, чем у Gin. | Хороший баланс, но Gin более распространён. |

### Выбор: Gin

Обоснование: для backend-портфолио важна узнаваемость стека, доступность примеров и простота развёртывания. Gin обеспечивает достаточную производительность для MVP и демонстрирует умение работать с основным Go-стеком.

## 2. ORM / работа с БД

### Сравнение GORM и sqlc

| Инструмент | Плюсы | Минусы | Verdict |
|------------|-------|--------|---------|
| **GORM** | Максимальная скорость разработки, авто-миграции, связи, hooks, огромная комьюнити. | «Магия» может скрыть ошибки, менее производительный на сложных запросах. | ✅ **Выбран** — быстрее доставляет MVP, проще демонстрирует архитектуру. |
| **sqlc** | Type-safe SQL, явность, высокая производительность. | Больше boilerplate, при изменении схемы нужно перегенерировать код. | Хороший выбор для production-like проекта с акцентом на SQL. |

### Выбор: GORM

Обоснование: MVP требует скорости прототипирования. GORM позволяет быстро описать модели, связи и миграции. В будущем, при необходимости, часть запросов можно переписать на raw SQL или `sqlc`.

## 3. Библиотеки

| Назначение | Библиотека | Обоснование |
|------------|------------|-------------|
| **JWT** | `github.com/golang-jwt/jwt/v5` | Стандартная, поддерживаемая библиотека для JWT в Go. |
| **Password hashing** | `golang.org/x/crypto/bcrypt` | Проверенный алгоритм, рекомендуемый OWASP. |
| **Migrations** | `github.com/golang-migrate/migrate/v4` | CLI + программный API, поддержка PostgreSQL, простота интеграции в Docker. |
| **Logging** | `log/slog` (stdlib Go 1.21+) | Стандартная библиотека, структурированные логи, JSON-формат. |
| **Configuration** | `github.com/spf13/viper` или `github.com/caarlos0/env`/stdlib | Для MVP достаточно переменных окружения с небольшой обёрткой; Viper — если нужна гибкость. |
| **WebSocket** | `github.com/gorilla/websocket` | Стандарт де-факто, полный контроль над соединениями. |
| **Testing** | `testify` + встроенный `testing` | `testify` — удобные asserts и mocks; `httptest` — тесты HTTP-handlers. |

### Выбор по конфигурации

- **Рекомендовано**: использовать `envconfig`-подход через переменные окружения (`github.com/kelseyhightower/envconfig` или самописный парсер).
- Viper избыточен для MVP, но допустим, если нужны файлы-конфиги.

## 4. Инфраструктура

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| База данных | **PostgreSQL** | Реляционная модель для users/projects/files, надёжность. |
| Кэш / pub-sub | **Redis** | Presence, pub/sub, rate-limit. |
| Контейнеризация | **Docker + Docker Compose** | Простота локального запуска. |
| CI/CD | **GitHub Actions** | Стандарт для портфолио. |

## 5. CRDT / collaborative editing

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| CRDT-клиент | **Yjs** | Готовая библиотека, `y-monaco` для Monaco Editor. |
| CRDT-сервер | **Opaquely binary blobs** | Go-сервер не интерпретирует CRDT-структуру, только хранит и ретранслирует. |

Причина: в экосистеме Go нет mature Yjs-аналога. Интерпретация CRDT на сервере не требуется для MVP.
